| Entra SSO depth | (not a prior matrix row) | — | **Audited 2026-09-30, two real gaps found and fixed; three hypothesized attacks confirmed not possible.** The SSO surface is a single pure token-exchange endpoint (`AuthController.ExchangeEntraIdToken` — no OIDC middleware, no JIT provisioning, no account-linking flow at all). Confirmed safe by tracing: cross-Entra-tenant impersonation (issuer is pinned to one configured Entra tenant + a globally-unique `Email` index means there's only ever one candidate account to match), default-Admin JIT provisioning (doesn't exist — an unmatched email is rejected, not auto-created), and unguarded account linking (no such mechanism exists to abuse). **Fixed: Entra SSO silently bypassed per-account TOTP MFA** that the password-login path enforces — a valid Entra id_token proves identity to Entra, not to R2WAI's own second factor. `AuthController.ExchangeEntraIdToken` now enforces the identical `MfaEnabled`/`totpService.ValidateCode` branch the password path already has; `EntraIdRequest` gained an optional `MfaCode`; the client (`LoginPage.tsx`/`AuthProvider.tsx`/`authClient.ts`) got a matching MFA-prompt retry flow, re-running MSAL to get a fresh id_token on the retry rather than resubmitting a stale one. **Fixed: uncached, thread-pool-blocking OIDC discovery fetch on every anonymous SSO attempt** — `EntraIdAuthService.ValidateEntraIdTokenAsync` called `OpenIdConnectConfigurationRetriever.GetAsync(...).GetAwaiter().GetResult()` synchronously with no caching on every call to this `[AllowAnonymous]` endpoint; replaced with a real `ConfigurationManager<OpenIdConnectConfiguration>` cache (the same mechanism the standard JWT-bearer pipeline already uses elsewhere), and the service registration moved `Scoped`→`Singleton` so the cache actually persists across requests. **Not fixed, flagged as a latent architectural gap, not a live exploit:** SSO config is a single global Entra tenant with no per-R2WAI-tenant binding — fine today (rules out the cross-tenant scenario above), but would need real design work before a second customer's own separate Azure AD tenant could safely SSO in. **Not tested with automated coverage:** the MFA-branch fix mirrors the password path's already-untested-by-name MFA logic exactly (grepped: no existing test in this codebase exercises either MFA branch by name) and building fake-Entra-token test infrastructure (a mock OIDC discovery endpoint, or an interface extraction) was judged disproportionate scope for this fix — verified by build, full regression suite, and close code review instead. |

| AI Model Gateway fallback/resilience | (not a prior matrix row) | — | **Closed 2026-09-30: cross-provider fallback implemented for `ChatAsync`/`StreamChatAsync`.** A new `IModelGateway.FallbackProviderName` (backed by an optional `AI:FallbackProvider` config key, same pattern as `AI:Provider`) lets `SemanticKernelService` retry once against a second provider when the primary either has no chat completion service configured at all, or fails at runtime — deliberately scoped to the two production-critical, user-facing chat entry points (not `GenerateResponseAsync`/`SummarizeTextAsync`/`ExtractDataAsync`/`CompareDocumentsAsync`, which are lower-traffic internal helpers where the added complexity wasn't justified). Only the fallback's provider *name* is forced on the config passed down to it — its `ApiKey`/`ModelId`/`Endpoint` deliberately stay null so each field falls back field-by-field to that provider's own `AI:{Provider}:*` configuration (the primary's resolved credentials would be wrong for a different provider). A misconfigured fallback (e.g. Ollama/Z.ai missing their required endpoint/key, which throw `ConfigurationException` synchronously) is caught and treated as "no fallback available" so it can never mask the original failure it was meant to recover from. Streaming fallback is deliberately narrower than non-streaming: it only retries **before any chunk has reached the caller** (tracked via a `streamedAny` flag) — a failure after real content was already streamed just propagates as before, since restarting against a different provider mid-stream would duplicate/garble what the client already rendered. Does **not** touch `ModelConfiguration`'s per-tenant schema (fallback is a process-wide config key, not a per-assistant setting) — no concrete demand for that granularity yet. Covered by 8 new unit tests (`SemanticKernelServiceFallbackTests.cs`) plus 2 in `ModelGatewayTests.cs`; full Infrastructure suite 337/337. The non-streaming chat path's own pre-existing degradation (clean structured JSON errors, correct 504 on timeout) is unchanged when no fallback is configured — this is additive, not a behavior change for the default (unset `AI:FallbackProvider`) case. **Previously fixed, still true: every SSE streaming chat path had zero error handling around the AI provider call.** `AssistantsController.StreamChat`, `ChatbotsController.StreamChat`, and `ChatController.StreamMessage` each now wrap their streaming loop in `catch (Exception ex) when (!ct.IsCancellationRequested)` and emit a graceful error frame (a named `error` SSE event for the first two, matching their own established convention for every other failure mode; a plain `data: {"error":...}` frame for the third, which has no named-event convention and no client caller in this codebase to begin with) instead of silently dropping the connection. `ExceptionHandlingMiddleware` also now checks `Response.HasStarted` before attempting to rewrite a response that already began streaming, as defense-in-depth for any other exception reaching it mid-stream. **Fixed: the WebSocket/SignalR chat path (`SendMessageCommand`) had no way to notify a passive watcher of a failed stream** — `IStreamingNotificationService` gained `SendStreamErrorAsync`, called from `SendMessageCommand`'s existing catch block (best-effort, never masking the real exception), broadcasting a real `StreamError` SignalR event; wired up client-side in `useChatSession.ts` (`streamError` state). The active sender's own `sendMessage()` promise already surfaced failure via its HTTP response — this specifically closes the gap for any other client that joined the same conversation group without being the one who sent the message (the interface's own documented "second tab / supervisor dashboard" case). |
