## 1. Executive Summary

**Verdict.** R2WAI today is a competent multi-tenant AI assistant / RAG / automation studio (.NET 10 + React) with a *governed-looking* tool-calling layer. It is **not yet a governed execution platform.** The things that make a *write* to an enterprise system safe — durable execution, idempotency, approval bound to the exact action, one tool gateway that every path uses, fail-closed governance — are missing, or are contradicted by code. Read-only assistant/RAG use is close to pilot-ready once the security P0s below are fixed. Anything that writes to a connected application is **not safe today**.

**Ten findings that decide the verdict** (all `[R]`, none executed):

1. **A rejected approval does not stop the workflow.** `ApprovalsController.Reject` calls `ResumeWorkflowAsync(..., "Rejected")` (`src/R2WAI.Api/Controllers/ApprovalsController.cs:193`); `WorkflowBridge.ResumeWorkflowAsync` never branches on the status (`src/R2WAI.Api/Services/WorkflowBridge.cs:261-310`) and runs the remaining steps. Nothing in `Api/Workflows` or `Api/Services` handles "Rejected" `[G]`.
2. **Duplicate external side effects are possible** — no idempotency key exists for tool or workflow execution `[G]`; the `HttpTool` client retries 3× on 5xx/408/network errors for *every* HTTP method including POST/PUT/DELETE (`src/R2WAI.Infrastructure/DependencyInjection.cs:54-61`); `RetryFailedStepAsync` re-runs the failed step (`WorkflowBridge.cs:318-377`).
3. **Every replica runs every sweeper**, and the shipped k8s manifest runs 2–6 replicas (`k8s/api-deployment.yaml:26,83-84`). Scheduled workflows and delayed resumes have no claim/lock (`WorkflowScheduleBackgroundService.cs:49-110`, `WorkflowDelayResumeBackgroundService.cs:53-69`); no distributed lock exists anywhere `[G]`.
4. **Governance fails open.** The audit/governance filter is attached *last*, inside a `try/catch` that swallows errors (`src/R2WAI.Infrastructure/AI/SemanticKernelService.cs:490-541`); a tool with no `ToolDefinition` row is *allowed* (`AiFunctionAuditFilter.cs:238`); built-in tool rows are seeded for the default tenant only (`ApplicationDbContextSeed.cs:289-311`); OpenAPI-discovered capabilities are created active with default risk "Low" and no approval (`DiscoverApplicationCommand.cs:83-86`, `ToolDefinition.cs:28,51`).
5. **The tenant filter fails open.** `TenantId == null || row.TenantId == TenantId` (`src/R2WAI.Infrastructure/Persistence/ApplicationDbContext.cs:311`); the tenant comes only from a JWT claim (`CurrentUserService.cs:23-30`); static API keys may carry no tenant (`ApiKeyAuthenticationMiddleware.cs:137-138`). The vector table has no tenant column (`PgVectorService.cs:36-44`).
6. **A fresh production database is seeded with known-password accounts** (`admin@r2wai.io` with Admin+SystemAdmin, a second tenant and its admin, all with passwords hard-coded in source): `DatabaseInitializer.cs:87-88`, `ApplicationDbContextSeed.cs:63,76,91,325`; only the `Testing` environment skips initialization (`Program.cs:471`).
7. **Anonymous account creation.** `POST /api/v1/auth/register-member` has no `[Authorize]` and there is no fallback policy (`AuthController.cs:535`); it creates a login-capable user in the "default" tenant from an Aadhaar number, and Aadhaar login uses an unsalted SHA-256 (`RegisterMemberCommand.cs:60-96`, `AuthController.cs:113-127`, `RegisterMemberCommand.cs:140-142`).
8. **SSRF.** The only egress guard is on the integration *Test* button (`IntegrationsController.cs:159,206-235`) and it is weak (blocks only `127.0.0.1`, not `127.0.0.2`; no IPv6/DNS checks). The real call path (`HttpTool.cs`), the knowledge-base URL fetcher (`KnowledgeBaseService.cs:199`) and the workflow "API Call" step (`ApiCallNodeProvider.cs:15-22`) have none.
9. **The workflow "API Call" step bypasses the Tool Gateway entirely** — raw Elsa `SendHttpRequest` with URL, method, body and headers taken from step config: no capability, permission, policy, audit, SSRF guard or credential handling. **Direct-endpoint integration credentials are stored in plain text** in `ToolDefinition.Configuration` (`CreateIntegrationCommandHandler.cs:16-18`, read back at `DynamicToolExecutor.cs:129-169`) — `ARCHITECTURE.md` says the opposite.
10. **Approvals are not an execution control.** Escalated requests can never be approved or rejected (`ApprovalService.cs:154,199` require `Pending`; `Escalate()` sets `Escalated`; `ApprovalStatus.Escalated` is referenced nowhere else `[G]`); there is no expiry state; an approval is not bound to a payload hash; an AI tool that needs approval is *hard-denied*, not parked (`AiFunctionAuditFilter.cs:135-142`).

**The most important test (Appendix D): NO.** R2WAI cannot today safely "find pending supplier requests → prepare updates → get approval → execute through the connected app → verify → survive restart → full audit". It stops at four places: parameterised reads are impossible (a dynamic tool has a fixed URL and only a free-text JSON body, which `HttpTool` drops for GET), approval cannot gate an AI action, the only governed write path does not exist (workflow HTTP step is ungoverned), and there is no verification, execution record or crash recovery.

**Direction (§63).** Keep the stack. Do not replace Elsa, Semantic Kernel or PostgreSQL. Build a small **Execution Kernel** inside the monolith: one `IToolGateway`, a durable `WorkflowRun/StepAttempt/ToolExecution` model with idempotency keys and leases in PostgreSQL, approvals bound to actions, fail-closed policy. Reposition Elsa as (at most) a step executor — its native resume is already bypassed by the code.

**What is genuinely good** (so this is not read as a teardown): clean layering; AES-256-GCM with env-only key in non-dev; constant-time API-key compare; TOTP MFA with a scoped-token enrolment flow; the anonymous chatbot never gets tools, is publish-gated and has a per-chatbot origin allowlist; tool-enabled kernels are cloned per request (no cross-request tool leakage); reflective tenant filter + a second seeded tenant used for isolation tests; background-job claim via atomic `UPDATE`; blocking Trivy scan; non-root API image; `xmin` concurrency tokens; real health checks; business metrics; a very honest habit of documenting workarounds in code comments.

## 4. Architecture

Modular monolith with Clean Architecture — **the right shape; keep it.** Two real deviations from the documented model:

- **Controllers bypass the Application layer.** `ApprovalsController`, `ApiKeysController`, `AuthController`, `AdminController`, `WorkflowsController` inject `ApplicationDbContext` directly `[R]`. MediatR behaviours (`AuthorizationBehavior`, `ValidationBehavior`) therefore protect only handlers routed through MediatR; the rest depend on per-action attributes.
- **Two workflow truths.** Elsa persists its own instance/definition/bookmark state; R2WAI persists `WorkflowInstance`/`WorkflowStepExecution`. The code treats R2WAI's rows as authoritative and re-starts a *new* Elsa run for every continuation (`WorkflowBridge.cs:247-260`, §20).

Concurrency-safety of the monolith itself: all five hosted services assume a single instance (§21).

## 11. AI

Chain (brief §5), traced:

`UI → Assistants/Chat controller → command/service → Prompt (template service, per-type fallback) → ModelGateway → Semantic Kernel (Auto function calling) → RAG pre-retrieval and/or tool → AiFunctionAuditFilter → tool → external system → result to model → response → AuditLog`

Where it breaks:

1. **Tool selection:** SK `FunctionChoiceBehavior.Auto()` with no explicit cap on tool iterations or per-conversation tool budget in code (`SemanticKernelService.cs:192,277`) `[G]`.
2. **Assistants with no explicit tool list get *every* built-in and *every* active HTTP tool of the tenant** ("null means not configured", `SemanticKernelService.cs:492-507`, `DynamicToolFunctionFactory.cs:51`) — combined with discovery-created "Low/no-approval" capabilities this is excessive agency by default.
3. **Governance can be absent** (finding 4).
4. **No prompt-injection defence:** retrieved text and tool output are concatenated into the prompt with no delimiting/untrusted-content policy; the only "sanitiser" strips leaked tool-call text from replies (`SemanticKernelService.cs:49-57`) `[G]`. The tool response is returned to the model unbounded (`HttpTool.cs:70`).
5. **Errors are swallowed to text:** tools return `"API call failed: …"` strings; vector search errors return an empty list; the model narrates "no results".
6. Structured response cards and tool-progress events are real and useful `[N]`.

## 20. Elsa

**What Elsa owns today `[R]`:** (1) runs a freshly built flowchart in-process until completion or the first bookmark; (2) the activity library used by step types — `SendHttpRequest`, `SendEmail`, `WriteLine`, plus R2WAI's `ApprovalStepActivity`, `InvokeSemanticKernelActivity`, `TransformStepActivity`; (3) persistence of definitions/instances/bookmarks/logs in PostgreSQL; (4) `UseScheduling`.

**What R2WAI owns `[R]`:** the authoritative instance and step state (`WorkflowInstance`, `WorkflowStepExecution`), approvals, delay scheduling (an Elsa Delay is **never executed** — `WorkflowBridge.cs:113-138`), retry, continuation, notifications, version pinning (weak — §21).

**Duplication: yes.**
- Two state stores for one run (Elsa instance + R2WAI instance).
- One Elsa definition is **re-created and re-published on every run** under the same `DefinitionId` (`WorkflowBridge.cs:225-230`) — unbounded version growth, and concurrent starts of the same workflow race on publish.
- Every approval/delay/retry starts a **new** Elsa run with its own definition id (`…-continue-…`, `…-delay-…`, `…-retry-…`, `WorkflowBridge.cs:302-304,365,409-411`).

**Why, according to the code:** native bookmark resume "does not work for these dynamically-built-and-republished-per-run Flowchart definitions… no fix exists in Elsa 3.7.1" (`WorkflowBridge.cs:247-260`) `[N]` not reproduced. **Hypothesis `[I]`:** resume needs the *same stable definition version the instance started with*; republishing a different definition per run breaks exactly that. This is testable in about a day.

**Is Elsa persistence sufficient?** Not as used — R2WAI does not rely on it. **Can Elsa coexist with an agent framework?** Yes; they solve different problems (business process vs AI step planning), but only once R2WAI owns a durable execution model.

**Decision: MODIFY, gated — do not REPLACE.**
1. *Spike (≤5 days):* publish **one Elsa definition per `WorkflowVersion` at publish time**; start instances by version; resume with native bookmarks; prove survival of an API restart with Testcontainers.
2. *If it passes:* delete rebuild-and-continue and the per-run publish.
3. *If it fails:* keep Elsa only as an activity/step library (or drop it) and let the R2WAI durable step runner (§56) be the engine. No other evidence in the source argues for replacing Elsa.

Also: `UseJavaScript()` is enabled — confirm no workflow JSON can carry expressions `[I]`; Elsa's REST API is not exposed (good).

## 22. Idempotency

- The **only** idempotency is chat send: `SendMessageCommand.cs:43-45,129-130` → `InMemoryIdempotencyStore`, a **singleton, process-local** (`DependencyInjection.cs:87`) — lost on restart, not shared between replicas.
- Tool execution: **no key**; `HttpTool` sends no `Idempotency-Key` (`HttpTool.cs:59-66`). Workflow start via webhook/schedule/AI: no key. Webhook replay: timestamp header exists, no event-id de-duplication `[G]`.
- **Stacked retries:** Polly ×3 (2/4/8 s) inside the tool call + the model re-calling a failed tool + UI "retry step" + duplicate sweepers.

**Brief §22 scenario (external API succeeds → R2WAI crashes before recording → restart → resume): CAN EXECUTE TWICE → P0.** The required `TenantId + WorkflowRunId + WorkflowStepId + IdempotencyKey` does not exist; the closest, `WorkflowStepExecution(InstanceId, StepIndex)`, has no uniqueness constraint and no external-effect record.

Target: `ToolExecution(TenantId, RunId, StepId, AttemptNo, IdempotencyKey UNIQUE(tenant,key), Status{Prepared,Sent,Succeeded,Failed,Unknown}, RequestHash, ResponseHash)`; send `Idempotency-Key` where the target supports it; for targets that do not, use *reconcile-before-retry* (call a read capability to check whether the effect exists) and never auto-retry non-idempotent methods.

## 56. Target Execution Model

1. **Propose:** the model returns an `ActionProposal` (capability + arguments); the gateway validates it against `InputSchema`.
2. **Decide:** identity → tenant → permission (RBAC+ABAC) → policy → risk. Deny by default; missing metadata ⇒ deny.
3. **Approve (if required):** create `ApprovalRequest(PayloadHash)`, set the run `WaitingApproval`, **release the worker**. Approval resumes by event; expiry is a timer; rejection ⇒ `Cancelled`.
4. **Prepare:** insert `ToolExecution(Prepared, IdempotencyKey)` in the same transaction as the step state (unique key ⇒ duplicate rejected).
5. **Send:** call the connector through the egress guard with the idempotency key; mark `Sent`. Non-idempotent targets are **never auto-retried**.
6. **Record:** mark `Succeeded/Failed`; on timeout/unknown ⇒ `Unknown`.
7. **Verify:** run the capability's verifier (a read capability); `Unknown` executions are **reconciled** (check whether the effect exists) before any retry.
8. **Audit:** `AuditEvent` + `ExecutionEvent` written in the same transaction (outbox for external notifications).
9. **Recover:** workers lease steps (`SKIP LOCKED`); expired leases are reclaimed and reconciled; sweepers become lease-based jobs; runs pin `WorkflowVersionId`.
10. **Cancel:** cooperative token + `Cancelled` state; in-flight `Sent` executions are reconciled, not assumed.

## 57. Target Agent Architecture

Autonomy ladder (never skip a rung; each rung gated per capability by risk):

`L0 Answer (RAG)` → `L1 Navigate/Explain` → `L2 Read (LOW capabilities)` → `L3 Propose action + human approve/execute` → `L4 Execute MEDIUM automatically with verification` → `L5 Scheduled/agentic workflows with policy budgets` → (`Digital employee`, `Multi-agent` only after L4 is reliable). HIGH/CRITICAL are never L4+. Planner (LLM) and executor (deterministic run engine) stay separate; agents get capabilities only through the gateway; every run has a tool-call/step/token/time budget; controlled learning only via human-validated procedures.
